# SwiftUI for Humans for Mac: plan and PRD

## Context

SwiftUI for Humans ships today on iPhone and iPad (TestFlight build 3, App Store app 6824033787). It's a catalog of 117 live pages in three tabs (Components, Design, Ship) that shows how SwiftUI renders on iOS and how to design and ship iOS apps.

The Mac app is **the Mac edition of the same idea, not a port**:
- SwiftUI components as they look and behave on macOS
- Mac design guidance (the macOS HIG)
- Mac best practices: windows, menus, keyboard, Settings
- How to ship Mac apps: sandbox, Mac App Store, notarization

It reuses the app's engine (page model, page scaffold, live demos, code blocks, Do / Don't, checklists, search, wallpapers, tips). The content is new and Mac-specific. Later tvOS and watchOS editions follow the same pattern: one engine, one content set per platform.

**What exploration found:**
- **The `.swiftpm` app package can't build a Mac app.** Xcode 27's `AppleProductTypes` only has `iOSApplication`, and its `.mac` device family means Mac Catalyst, not native macOS. It has no tvOS or watchOS option either.
- **The engine is mostly portable.** Catalog/ is 15 files, about 3,300 lines. Seven of them touch UIKit or iOS-only modifiers:
  - `CodeBlock` (UIPasteboard, UIFont)
  - `PageWallpaper` (UIGraphicsImageRenderer grain)
  - `PageParts` (`.topBarTrailing`, `.inlineLarge`, hover effect)
  - `DemoPage` (sheet detents, size class)
  - `PageSections` (size class)
  - `PhoneScreen` and `LargeTitleExpander` (UIKit only)
- **The app shell is iPhone and iPad shaped.** It's a `TabView` holding a split view per tab, branches on `horizontalSizeClass` in about 15 places, and uses `Color(.systemGroupedBackground)`.
- **No test target exists today.**

## Decisions

| Decision | Choice |
|---|---|
| Mac app scope | Separate Mac edition: same tabs (Components, Design, Ship), all-new Mac content |
| App Store | Universal Purchase: same bundle ID `com.swiftuiforhumans.app`, macOS platform added to the existing App Store Connect record, shared tip products |
| Targets | One app target per platform (iOS now, macOS now, tvOS and watchOS later) plus a Swift Testing target |
| Project format | Xcode project generated by XcodeGen from `project.yml`, using **synchronized folders** so adding a page never touches the `.pbxproj` |
| Playgrounds `.swiftpm` | **Drop it** (recommendation; see below) |
| Min OS | macOS 26 (matches iOS 26 and Liquid Glass) |

**Why drop the `.swiftpm`.** You asked for a recommendation:
1. **It can't build the Mac app.** We need an Xcode project no matter what.
2. **Keeping it means two builds of the iOS app.** Its Package.swift, Info.plist and file layout would sit beside the Xcode project, and they would drift.
3. **Nothing you described needs Playgrounds.** The app ships through the App Store, and `ship` already supports `.xcodeproj`.
4. **The project helps in other ways.** Universal Purchase is easier with both apps in one project (one bundle ID, side-by-side versions). The test target you asked about also needs a real project.

The only thing we give up is opening the source in Swift Playgrounds on an iPad.

## Architecture

```
project.yml                      XcodeGen spec (source of truth for targets and settings)
SwiftUIForHumans.xcodeproj       generated and committed; synced folders, so adding files doesn't change it
SwiftUIForHumans/
  Shared/                        the engine, compiled into every app target
    Catalog/                     ComponentPage, PageScaffold, DemoPage, ExampleCard, CodeBlock, RichText,
                                 Checklist, PageSections, Scenery, PageWallpaper, Platform.swift (shims)
    App/                         Engagement, TipJar, AboutView/AppInfo, LaunchOptions, OverviewView, CatalogLinks
  iOS/                           the iOS edition; today's app with no behavior change
    App/                         @main, ContentView (TabView), SearchTab, Buddy, DocsBrowser, CatalogCommands, HeroReel, HeroTiles
    Catalog/                     PhoneScreen, LargeTitleExpander, PageScrubber
    Examples/                    the existing 15 groups, moved unchanged
    Edition.swift                ComponentCategory (iOS), Catalog.pages, tab intros
    AdditionalInfo.plist
  macOS/                         the Mac edition
    App/                         @main MacApp, MacContentView, MacCommands, SettingsView, DemoWindows
    Catalog/                     MacWindowFrame (mock window chrome for inline previews)
    Examples/<Group>/            new Mac pages, one folder per group
    Edition.swift                ComponentCategory (macOS), Catalog.pages, tab intros
    SwiftUIForHumans.entitlements    sandbox, network client
  Resources/                     Assets.xcassets (iOS and Mac icons), PrivacyInfo.xcprivacy
Tests/
  Shared/   iOS/   macOS/        Swift Testing; macOS tests are hosted by the Mac app (no simulator)
StoreKit/Tips.storekit           set as the scheme's StoreKit config for both apps
scripts/build.sh                 one build at a time (mkdir lock), -jobs 4, ARCHS=arm64
scripts/mac-shot.sh              opens the Mac app in the background with flags and screenshots its window
```

**Edition contract.** All of these are one module per app target, so no `public` API is needed:
- Each edition defines `enum ComponentCategory` with `title`, `symbol`, `blurb` and `tab`.
- Each edition defines `Catalog.pages` and `AppTab.intro`.
- `Shared/` compiles against whichever edition it's built with.
- Shared code may never name a page or an edition-only type. The other platform's build catches it if it does.
- Move files with `git mv` so history follows them.

**Platform shims** (`Shared/Catalog/Platform.swift`) keep `#if os` out of pages:
- `Pasteboard.copy(_:)`
- `Color.catalogGroupedBackground`
- `openExternally(_:)`
- an `isCompactLayout` environment value: the size class on iOS, always false on Mac
- `.catalogPageTitle()`
- `.catalogHover()`
- the grain image drawn with `CGContext` instead of UIKit

The pages themselves never use `#if os`. They belong to one edition.

**Mac shell (macOS 26):**
- **Layout.** One `NavigationSplitView` per window. The sidebar has a Components / Design / Ship switcher at the top, like Xcode's navigators, then category sections. The detail column shows the page or the tab's overview (wallpaper at the top). A toolbar search field filters the sidebar and opens results.
- **Scenes:**
  - `WindowGroup(for: ComponentPage.ID.self)` with state restoration
  - a `Settings` scene (⌘,) with Preview Appearance and the wallpaper look
  - a standard About panel plus the About window
  - a `DemoWindow` scene so pages like Toolbar, NavigationSplitView and Window styling can open **real windows** ("Open as Window")
- **Menus.** A Go menu (⌘1–3, ⌘[ / ⌘]), Help menu links, Sidebar and Inspector commands.
- **DemoPage controls** live in an `.inspector`.
- **Links.** Apple-site links open in the default browser. The in-app DocsBrowser stays iOS-only.
- **Ratings and tips.** `requestReview` and StoreKit tips work as on iOS. The buddy stays off.

## PRD: SwiftUI for Humans for Mac

**Problem.** Mac SwiftUI is poorly documented compared with iOS. Defaults differ (Toggle is a checkbox, Form uses columns, Picker is a pop-up), Mac-only APIs (`Settings`, `MenuBarExtra`, `Commands`, `Table`, windows) have few live examples, and most "SwiftUI on Mac" apps feel like iPad ports.

**Audience.** Developers and designers building Mac apps with SwiftUI, from first-timers to iOS developers moving to the Mac.

**Goals:**
1. Every Mac-relevant SwiftUI component is shown live as it really renders on macOS, with copyable code that compiles.
2. Mac design guidance follows the macOS HIG and is paraphrased and linked, never copied.
3. Mac conventions are demonstrated: menus, shortcuts, windows, Settings, keyboard navigation, pointer, drag and drop.
4. A practical shipping track: Mac App Store, Universal Purchase, sandbox, TestFlight for Mac, Developer ID and notarization.
5. The app itself is an exemplary Mac app. It follows its own advice: real menus, resizable and restorable windows, ⌘, Settings, full keyboard use.

**Non-goals for v1:**
- Mac Catalyst or "Designed for iPad" content
- tvOS and watchOS
- a website section for the Mac app (only privacy and support wording changes)
- the buddy on Mac
- a Mac hero reel

**Requirements:**
- **R1.** Native macOS 26 app target, same bundle ID (Universal Purchase), sandboxed, with the app category set to Developer Tools.
- **R2.** The iOS app builds from the new project with **no visible change**. Screenshots of the Overview and ButtonExample pages must match the current build.
- **R3.** The shared engine compiles for both platforms, and pages stay platform-pure.
- **R4.** The Mac shell described above: split view, tab switcher, search, Settings, menus, multiple windows, restoration, demo windows.
- **R5.** Content: about 95 Mac pages, listed below. Each page follows `docs/content-guide.md` plus a new `docs/mac-content-guide.md`:
  - Mac vocabulary: click, menu bar, window, ⌘⌥⇧⌃
  - macOS HIG links
  - Scenery-only imagery
  - Do / Don'ts sized for Mac
- **R6.** Swift Testing target. Tests cover:
  - registry integrity per edition: unique IDs, valid `related` IDs, every category has a tab
  - `SearchQuery`
  - `LaunchOptions`
  - `SeededRandom` determinism
  - the `AppleSites` allow-list
- **R7.** Launch flags on Mac match iOS: `-tab`, `-open`, `-search`, `-showControls`, `-scrollTo`. That allows automated screenshots.
- **R8.** App Store readiness:
  - a Mac app icon
  - the privacy manifest
  - export compliance (`ITSAppUsesNonExemptEncryption`)
  - `website/privacy.html` and `website/support.html` mention the Mac
  - a TestFlight for Mac build

## Execution phases

**Phase A: Restructure.** Serial, in this session. Everything else depends on it.
1. Commit this PRD as `docs/mac-prd.md`.
2. `brew install xcodegen`. Confirm it supports `type: syncedFolder`. If it doesn't, generate classic groups, gitignore the `.xcodeproj`, and regenerate it inside `scripts/build.sh`.
3. `git mv` into the `Shared/`, `iOS/` and `Resources/` layout. Write `project.yml` with the iOS target and the test target. Point the scheme at `Tips.storekit`.
4. Delete `Package.swift`. Run `ship init --force` against the project, then `ship doctor`.
5. Add `scripts/build.sh`.
6. Write the first tests (R6) against the iOS edition.
7. Update the README, AGENTS.md and building-pages.md: the build command, the folder rules, and "Shared is the engine".

**Gate A:**
- The iOS build passes.
- iOS tests pass on the test simulator.
- Screenshots of Overview and Button on the dedicated test simulator match a baseline taken before the move.

**Phase B: Engine and Mac shell.** Serial, in this session.
1. Add `Platform.swift` shims. Move the iOS-only engine pieces to `iOS/Catalog`.
2. Split `ComponentCategory`, `Catalog.pages` and the tab intros into each edition's `Edition.swift`.
3. Add the macOS target to `project.yml`: entitlements, Mac icon, `LSApplicationCategoryType`, and `AdditionalInfo.plist` for the Mac too.
4. Build the Mac shell (R4), `MacWindowFrame`, `DemoWindow` and `scripts/mac-shot.sh`.
5. Pre-create the Mac `Edition.swift` with all categories, and one empty `<Group>Pages.swift` per group. Fan-out writers then only touch their own folder.
6. Write **three reference pages**: Mac Toggle (DemoPage), Settings scene (ArticlePage with a demo window), and Mac App Sandbox (Ship checklist).
7. Write `docs/mac-content-guide.md`.

**Gate B:**
- Both apps build, and both test suites pass.
- The Mac app launches and the three reference pages screenshot correctly in light and dark.
- You review the reference pages: they set the bar for the fan-out.

**Phase C: Content fan-out.** Dynamic workflow.
- **Writers.** Six to eight agents, one per group in the content map. Each works in its **own worktree** and touches only `macOS/Examples/<Group>/`.
- **Builds.** All builds go through `scripts/build.sh`'s lock, so only one runs at a time.
- **Snippet checks.** Each writer verifies snippets in `_SnippetCheck<Group>.swift` and deletes the file before finishing.
- **URLs.** Each writer checks every URL with `curl -sI`.
- **Screenshots.** Each writer screenshots every page with `mac-shot.sh` and looks at it.
- **Review.** Each group gets an adversarial review pass: content guide, compile, URLs, Mac-correctness of claims, and Do / Don't legibility.
- **Size.** About 10 agents, so the workflow size guideline may need raising.

**Phase D: Integration.** Serial.
1. Merge the group branches.
2. Do a full build of both platforms and run the tests, including the cross-group `related` ID check.
3. Screenshot every page, light and dark.
4. Fix what turns up.

**Phase E: Ship.** Serial, with you involved.
1. Add the macOS platform to the App Store Connect app record (you do this in App Store Connect).
2. Final Mac icon.
3. Update `website/privacy.html` and `website/support.html`.
4. Archive and upload. If `ship` can't export a Mac `.pkg` (today it's `.ipa`-only), fall back to `xcodebuild archive` plus `-exportArchive` (`method app-store-connect`) and an upload through Xcode Organizer.
5. TestFlight for Mac.

## Verification

- **iOS:** `scripts/build.sh ios`, install on the dedicated test simulator, and compare axe screenshots of Overview and Button against the pre-move baseline.
- **macOS:** `scripts/build.sh mac`. Then `scripts/mac-shot.sh -open <id>` for every page, which launches in the background with `open -g` and captures the window with `screencapture -l`, in light and dark.
- **Tests:** `xcodebuild test -scheme CatalogTests-macOS`, which runs on the Mac with no simulator.
- **Content:** snippet compile checks, `curl -sI` on every URL, and the registry tests.
- **Release:** a TestFlight for Mac build installs and runs on your Mac.

## Risks and open items

- **Rendering demos of windowed UI inline.** Toolbars and split views inside a page can take over the window's toolbar, like the iOS nav-bar issue. Mitigation: a static `MacWindowFrame` mock inline plus a real `DemoWindow`. Prove this out on the reference pages in Phase B.
- **Mac windows on your screen.** Screenshot runs open real Mac windows. `open -g` keeps them in the background, but they're still on your desktop. There's no Mac equivalent of a dedicated test simulator.
- **XcodeGen synced-folder support.** Verify it in Phase A; the fallback is described there.
- **`ship` and macOS.** It exports `.ipa` only today, so the Mac upload probably needs the fallback path.
- **Universal Purchase build numbers.** Confirm App Store Connect's rules for macOS and iOS build trains when the Mac platform is added.
